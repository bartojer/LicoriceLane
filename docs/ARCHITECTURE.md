# Architecture

Reviewed against the working tree on October 9, 2026. This is a navigation guide to current code. [STATUS.md](STATUS.md) records unfinished behavior and verification gaps.

## Application boundaries

Business queries and write operations belong in `LicoriceLane` contexts under `lib/licorice_lane`. Routes, authentication, LiveViews, LiveComponents, and reusable UI belong under `lib/licorice_lane_web`. Schema namespaces do not always match context names: `Inventory` operates on `Items` and `Locations` schemas, and there is no separate `Items` or `Locations` context.

| Area | Context / service | Schema files | UI entry points |
| --- | --- | --- | --- |
| Accounts | [accounts.ex](../lib/licorice_lane/accounts.ex) | `accounts/user.ex`, `accounts/user_token.ex` | [user_auth.ex](../lib/licorice_lane_web/user_auth.ex), `live/user_*`, session controller |
| Inventory | [inventory.ex](../lib/licorice_lane/inventory.ex) | `items/item.ex`, `items/single_item.ex`, `locations/items_location.ex` | [InventoryLive](../lib/licorice_lane_web/live/inventory_live.ex), admin inventory/add/edit components |
| Locations | Operations currently use schemas/Repo directly in seeds and fixtures | `locations/location.ex`, `locations/location_history.ex` | Warehouse selection in admin item forms |
| Customers | [customers.ex](../lib/licorice_lane/customers.ex) | `customers/customer.ex` | Admin clients component |
| Rentals / bookings | [rentals.ex](../lib/licorice_lane/rentals.ex), [lifecycle.ex](../lib/licorice_lane/rentals/lifecycle.ex) | `rentals/rental.ex`, `rental_allocation.ex`, `rental_single_item.ex`, `rental_bulk_item.ex` | Admin bookings and dashboard components |
| Messages | [messages.ex](../lib/licorice_lane/messages.ex) | `messages/message.ex` | [ContactLive](../lib/licorice_lane_web/live/contact_live.ex), admin messages component and unread badge |
| Cache | [cache.ex](../lib/licorice_lane/cache.ex) | None | Write-path invalidation; query caching is not currently wired in |

Schema paths in the table are relative to `lib/licorice_lane`. The [router](../lib/licorice_lane_web/router.ex) is the source of truth for URLs. Marketing pages use `PageController` and templates under `controllers/page_html`; `/contact` uses `ContactLive` rather than the older contact template.

## Startup and configuration

[Application](../lib/licorice_lane/application.ex) supervises telemetry, Repo, the Cloak Vault, DNSCluster, PubSub, Finch, Cachex, and the endpoint. Cachex runs as `:admin_cache` with a five-minute default TTL and cleanup every 30 seconds.

[config/config.exs](../config/config.exs) defines shared settings, asset tools, and the default local mailer. Development and test files supply local database settings and distinct fixture encryption keys. [runtime.exs](../config/runtime.exs) reads production secrets and release HTTP settings. [mix.exs](../mix.exs) defines setup, database, test, and asset aliases; check the aliases before invoking a setup/reset command.

## Inventory relationships and writes

- `Item` is the base record with category, item type, price, image path, color, and `min_stock`.
- A single item has one `SingleItem`. Its non-autogenerated primary key is also the foreign key to `Item.id`. It stores condition, status, and current location. Each physical unit has its own `Item` record.
- A bulk item has `ItemsLocation` rows, each relating an item to a location with a quantity. One `Item` represents all units of that type.
- `Location` is a warehouse or customer location; customer locations can reference a customer.
- `LocationHistory` relates an item, source/destination locations, quantity, timestamp, and optional rental. Its schema does not by itself implement movement workflows.

Use `Inventory.create_item_with_location/1` for item creation. It validates and normalizes attributes, inserts the item and its location data in one `Ecto.Multi` transaction, then invalidates cache entries and broadcasts after success. It returns a fully preloaded item. See the [item creation guide](../ITEM_CREATION_GUIDE.md) for input and error contracts.

Single item changesets normalize `min_stock` to `0`. The creation context supplies `10` for a bulk item when the attribute is absent; the base `Item` schema itself defaults to `0`. Do not assume direct schema/Repo inserts use the context default.

Warehouse stock queries aggregate `ItemsLocation` rows at warehouse locations. Low-stock queries compare that aggregate with `min_stock`; single items normalized to `0` do not trigger the threshold. Category values are the enums on [Item](../lib/licorice_lane/items/item.ex); the UI's `lighting` filter groups `:candle` and `:electric_light`.

`update_item/2` updates base item fields. Admin edits use `update_item_with_details/2` to update base fields and single-item condition/status in one transaction, including an image path change. Both APIs invalidate inventory data and broadcast after success. Neither provides a general operation for moving a single item or editing bulk quantity/location rows. New movement or rental write paths should handle all affected records in the context and invalidate any affected inventory/rental data.

`delete_item/1` removes stock rows and the base item in one transaction; the database cascades deletion to single-item tracking. Locations and shared image files remain. Foreign key constraints reject items used in any booking or location history, including returned/cancelled bookings, and roll back stock removal. Reference violations and stale deletes return `{:error, changeset}`; cache invalidation and broadcasts occur only after success. Admin inventory uses a server-held selection and a confirmation modal, shows the result in the component, and reloads the current filtered page with bounds clamping. Cancellation performs no write.

## Customers, encryption, and search

[Customer](../lib/licorice_lane/customers/customer.ex) encrypts phone, email, contact person, billing address, and notes with `LicoriceLane.Encrypted.Binary`; the Vault uses AES-GCM. Name remains plaintext. Changesets populate email/phone hash fields using `Cloak.Ecto.SHA256`. Context queries support name substring search plus exact email/phone matches and deduplicate combined results.

The custom [HMAC type](../lib/licorice_lane/hashed/hmac.ex) is configured but unused by the current customer and message schemas. Production nevertheless requires `HMAC_SECRET` because runtime configuration explicitly reads it. See [encryption notes](../ENCRYPTION_IMPLEMENTATION_STATUS.md) before changing key management or lookup behavior.

Customer search pagination currently builds the combined search result list and slices it in memory. The unfiltered customer list uses database pagination. Avoid introducing partial matching over encrypted fields or logging loaded customer structs.

Admin ClientsComponent provides a details modal with all customer fields and recorded locations, plus shared creation/editing forms for name, contact person, email, phone, billing address and notes. `Add New Client` opens a blank form; `Customers.change_customer/2` validates drafts, `create_customer/1` inserts new records and `update_customer/2` persists existing records. Both writes invalidate dependent cache entries only after success. The existing schema requires name, validates email, and accepts phone in `123-4567` format. Optional fields can be cleared; clearing email/phone also clears their lookup hash columns so old exact searches no longer match.

The component keeps the selected customer and creation/edit mode on the server and ignores IDs supplied in save parameters. Validation errors retain the form; cancellation discards it. Successful saves close the form, show a created/updated notice, and reload the current searched page, clamping bounds if an edit removes a matching row. Creation retains search/page even if the new record is outside that filter. Component updates and message-badge refreshes preserve an open creation/edit form. Missing/malformed selections return an unavailable notice; edits to a deleted record return an error changeset rather than raising. Closing a modal reloads the list without resetting search/page. Saving with no active create/edit form is ignored, so replaying a completed creation cannot insert another record.

## Rentals and booking terminology

Bookings and rentals refer to the same `Rental` entity. `RentalSingleItem` connects a rental to a `SingleItem`; `RentalBulkItem` connects a rental to an `Item` with a quantity.

`Rentals` provides read queries plus managed booking creation, advisory availability checks, allocation replacement, checkout, cancellation and partial returns. The atomic implementation is [rentals/lifecycle.ex](../lib/licorice_lane/rentals/lifecycle.ex). `RentalAllocation` records item, original source warehouse, booked quantity and returned quantity; single/bulk summary rows retain the originally booked quantities across returns.

`get_rental/1` preloads customer plus single-item names/current locations and bulk-item names/quantities for the admin details modal. `change_rental_details/2` and `update_rental_details/2` accept only event type/date, pickup (`rented_at`) and due date (`return_by`). Pickup/due dates are required; due cannot precede pickup and pickup cannot follow a recorded actual return. Event fields remain optional. Inputs without timezone offsets are interpreted as UTC; the admin datetime inputs explicitly label UTC and preserve seconds when submitting an unchanged form.

Managed bookings start `:reserved`; booking/reallocation reserves stock for a strictly positive half-open `[rented_at, return_by)` window without physical movement. Capacity is warehouse stock plus managed outstanding units promised back to that source, checked against peak simultaneous demand. Adjacent bookings can share stock; overdue unreturned units occupy an open-ended interval until returned. Availability checks are advisory; saves check again under locks. A customer-owned destination is required, and a new venue can be created atomically with the booking.

Checkout cannot precede pickup or follow the due date; it rechecks availability and actual stock, moves singles/bulk stock to the customer's destination, records movement history, and sets `:active`/`checked_out_at`. Return quantities are bounded by that booking's individual allocation and actual destination stock; partial returns go to each original source warehouse. Status becomes `:returned` and `returned_at` is set only after every allocation is returned. Cancellation applies only before checkout, releases reservations and retains booking references without stock movement.

Writers lock their rental, sorted parent Item IDs, then locations/stock. Item locks also protect missing destination stock rows and concurrent reservation inserts. A lifecycle version rejects stale/replayed operations; managed schedule edits check capacity and increment it. Pickup is fixed after checkout, and terminal schedules are fixed; event-only corrections remain possible for overdue bookings. Inventory edits use the same item locks, forbid type changes and reject status changes controlled by live bookings. Deletion locks the item before stock and retains all booking/history references. Quantity totals and additions respect SQL integer bounds.

The additive migration marks existing bookings `inventory_managed: false`; seeds and legacy fixtures keep that default. Their metadata edits retain the earlier row-lock/snapshot checks without inferred stock movements. Stock actions remain unavailable until a separate reconciliation workflow is implemented. Items referenced by active/late legacy rentals cannot enter managed bookings because their physical source/state is unknown. No legacy data is deleted or backfilled.

BookingsComponent supports all managed actions, numeric-order allocation rows and retained reservation/return drafts. Successful actions close the form and reload the filtered page; forged IDs cannot replace the server-held booking selection. AdminLive forwards rental updates to active bookings/dashboard components. Read-only details reload current data; edit/allocation/return forms retain snapshots so concurrent changes report conflicts.

`list_rentals_paginated/2` accepts `:date_filter` in its options as a `Date` or ISO 8601 date string. It combines the status query with an `event_date` range from midnight UTC inclusive to the next midnight exclusive before counting and paginating. Selected dates exclude rentals with missing event dates; blank, missing, or invalid dates leave the status query unchanged. This filter uses event date, independently of pickup date (`rented_at`).

- Stored statuses: `:reserved`, `:active`, `:returned`, `:late`, `:cancelled`.
- Upcoming queries include managed reservations, omitting their cancelled/returned bookings; legacy rows retain the existing future-pickup rule. A separate Reserved filter is available.
- Active queries check `status == :active` without excluding future dates.
- Overdue queries require past `return_by`, missing `returned_at`, and status in `[:active, :late]`.
- Event type is an enum of wedding, corporate, or birthday; dates use UTC datetimes.

Overdue classification is computed from dates; it does not require an automatic status-writing job.

## Admin shell and shared presentation code

[AdminLive](../lib/licorice_lane_web/live/admin/admin_live.ex) owns the active tab, editing item ID, and new-message count. It renders tab-specific LiveComponents from the same directory: dashboard, inventory, add item, edit item, bookings, clients, and messages. Component events target the component; navigation requests use `send(self(), ...)` messages handled by the parent LiveView.

Admin routes use both authentication/admin plugs and LiveView `on_mount` hooks. `Accounts.User.admin` defaults to false and is not cast by registration. [README](../README.md#local-admin-access) explains local account bootstrap.

[AdminHelpers](../lib/licorice_lane_web/helpers/admin_helpers.ex) holds labels, price/date formatting, truncation, pagination metadata, and the default page size of 25. [Pagination](../lib/licorice_lane_web/components/pagination.ex) renders pagination controls. Context pagination functions return `{records, total_count}` and use [Pagination](../lib/licorice_lane/pagination.ex) to clamp page bounds before fetching rows. Queries include a unique ID tie breaker so equal names/timestamps have stable page boundaries. Components use the same bounds for metadata, preserve filters/page on updates, and reset streams after changing filters or pages. Booking status/date controls are inside forms so LiveView can send change events. Both filters reset the page; the selected event date is bound to the input and retained during pagination/component refresh. Clearing the date restores all dates while retaining status. Invalid date strings clear the date filter; malformed date event payloads are ignored. Public inventory has its own presentation helpers in [inventory_components.ex](../lib/licorice_lane_web/components/inventory_components.ex).

## Cache and realtime contracts

`Cache` exposes fetch/get/put/clear helpers and four invalidation functions. Current inventory, customer, and message writes call invalidation, but application query paths do not call `Cache.fetch/get/put`. Do not describe the current lists or dashboard as cached simply because Cachex is supervised.

| Invalidation function | Keys removed |
| --- | --- |
| `invalidate_inventory/0` | `:inventory_items`, `:low_stock_items`, `:dashboard_stats` |
| `invalidate_customers/0` | `:customers`, `:dashboard_stats` |
| `invalidate_rentals/0` | `:rentals`, `:dashboard_stats` |
| `invalidate_messages/0` | `:messages`, `:new_messages_count` |

Managed rental writes invalidate both rental and inventory caches after success and broadcast rental/inventory updates. Legacy metadata edits invalidate rentals. Failed, deleted, stale writes and advisory checks retain cache entries and do not broadcast. Direct Repo writes bypass these contracts.

| Topic | Emitted messages | Producers / current consumers |
| --- | --- | --- |
| `"inventory:updates"` | `{:inventory_updated, item_id}` | Successful item creation/update/deletion; public InventoryLive reloads its listing, AdminLive refreshes the active dashboard/inventory component |
| `"messages"` | `{:message_created, message}`, `{:message_updated, message}` | Successful message creation/admin update; AdminLive refreshes its new-message count and active messages component |
| `"rentals:updates"` | `{:rental_updated, rental_id}` | Successful managed lifecycle or event/schedule write; AdminLive refreshes active bookings/dashboard components |

AdminLive owns these subscriptions and explicitly sends updates to the active component: inventory events reload the dashboard or inventory list; message creation/update events reload the messages list and refresh the unread badge; rental schedule updates reload the dashboard or bookings component. Inactive tabs load current data when mounted. List refreshes retain search/category/status/date filters and the current page, clamping the page when the filtered list shrinks. Dashboard streams are configured once in `mount/1` so repeated refreshes can safely reset them.

For an updated message selected in the detail modal, MessagesComponent reads its current database state by ID rather than applying a potentially older queued broadcast. Unsaved internal notes are tracked separately from the selected record and survive refreshes; clean notes follow external changes. Notes still save on blur, and saving them does not overwrite a concurrently changed status. Add/edit forms and their upload selections are retained during broadcasts. Message deletion invalidates cache entries but does not broadcast a deletion event; there is currently no admin deletion UI for messages.

## Upload storage

Admin add/edit components keep their file inputs mounted during previews and initialize separate upload configurations once in `mount/1`. Routine component updates preserve form/upload state; changing the edited item cancels the previous selection. Add success cards display the saved image.

[InventoryImageUpload](../lib/licorice_lane_web/helpers/inventory_image_upload.ex) coordinates upload consumption with context persistence. It copies a completed image, runs the inventory save, and consumes only on success. Database or storage errors postpone consumption so correction/retry or cancellation can use the same temporary image. Failed-save copies are removed. Ecto transactions do not roll back filesystem writes.

[ImageStorage](../lib/licorice_lane/inventory/image_storage.ex) creates UUID filenames and uses the application's `priv/static/uploads` directory by default. `INVENTORY_UPLOAD_DIR` configures another local directory at runtime; a dedicated `/uploads` static plug resolves the same directory for serving. PostgreSQL stores only the `/uploads/...` path. Replaced images remain on disk because paths may be shared; automated old-image cleanup is not implemented. Storage remains local; see [status](STATUS.md#verification-gaps) for deployment concerns.

[Upload regressions](../test/licorice_lane_web/live/inventory_upload_test.exs) cover real admin component selection, saving/serving, retries, cancellation, parent/component refresh, storage errors, add/edit transitions, switching edited items, and rejected files. An optional [Playwright browser case](../test/browser/inventory_upload.cjs) exercises the actual JavaScript preview and upload flow; README documents its runtime settings.
