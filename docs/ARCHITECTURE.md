# Architecture

Reviewed against the working tree on October 9, 2026. This is a navigation guide to current code. [STATUS.md](STATUS.md) records unfinished behavior and verification gaps.

## Application boundaries

Business queries and write operations belong in `LicoriceLane` contexts under `lib/licorice_lane`. Routes, authentication, LiveViews, LiveComponents, and reusable UI belong under `lib/licorice_lane_web`. Schema namespaces do not always match context names: `Inventory` operates on `Items` and `Locations` schemas, and there is no separate `Items` or `Locations` context.

| Area | Context / service | Schema files | UI entry points |
| --- | --- | --- | --- |
| Accounts | [accounts.ex](../lib/licorice_lane/accounts.ex) | `accounts/user.ex`, `accounts/user_token.ex` | [user_auth.ex](../lib/licorice_lane_web/user_auth.ex), `live/user_*`, session controller |
| Inventory | [inventory.ex](../lib/licorice_lane/inventory.ex) | `items/item.ex`, `items/single_item.ex`, `locations/items_location.ex` | [InventoryLive](../lib/licorice_lane_web/live/inventory_live.ex), admin inventory/add/edit components |
| Locations | Operations currently use schemas/Repo directly in seeds and fixtures | `locations/location.ex`, `locations/location_history.ex` | Warehouse selection in admin item forms |
| Customers | [customers.ex](../lib/licorice_lane/customers.ex) | `customers/customer.ex` | Admin clients component |
| Rentals / bookings | [rentals.ex](../lib/licorice_lane/rentals.ex) | `rentals/rental.ex`, `rentals/rental_single_item.ex`, `rentals/rental_bulk_item.ex` | Admin bookings and dashboard components |
| Messages | [messages.ex](../lib/licorice_lane/messages.ex) | `messages/message.ex` | [ContactLive](../lib/licorice_lane_web/live/contact_live.ex), admin messages component and unread badge |
| Cache | [cache.ex](../lib/licorice_lane/cache.ex) | None | Write-path invalidation; query caching is not currently wired in |

Schema paths in the table are relative to `lib/licorice_lane`. The [router](../lib/licorice_lane_web/router.ex) is the source of truth for URLs. Marketing pages use `PageController` and templates under `controllers/page_html`; `/contact` uses `ContactLive` rather than the older contact template.

## Startup and configuration

[Application](../lib/licorice_lane/application.ex) supervises telemetry, Repo, the Cloak Vault, DNSCluster, PubSub, Finch, Cachex, and the endpoint. Cachex runs as `:admin_cache` with a five-minute default TTL and cleanup every 30 seconds.

[config/config.exs](../config/config.exs) defines shared settings, asset tools, and the default local mailer. Development and test files supply local database settings and distinct fixture encryption keys. [runtime.exs](../config/runtime.exs) reads production secrets and release HTTP settings. [mix.exs](../mix.exs) defines setup, database, test, and asset aliases; check the aliases before invoking a setup/reset command.

## Inventory relationships and writes

- `Item` is the base record with category, item type, price, image path, color, and `min_stock`.
- A single item has one `SingleItem`. Its non-autogenerated primary key is also the foreign key to `Item.id`. It stores condition, status, and current location. Each physical unit has its own `Item` record.
- A bulk item has `ItemsLocation` rows, each relating an item to a location with a quantity. One `Item` represents all units of that type.
- `Location` is a warehouse or customer location; customer locations can reference a customer.
- `LocationHistory` relates an item, source/destination locations, quantity, timestamp, and optional rental. Its schema does not by itself implement movement workflows.

Use `Inventory.create_item_with_location/1` for item creation. It validates and normalizes attributes, inserts the item and its location data in one `Ecto.Multi` transaction, then invalidates cache entries and broadcasts after success. It returns a fully preloaded item. See the [item creation guide](../ITEM_CREATION_GUIDE.md) for input and error contracts.

Single item changesets normalize `min_stock` to `0`. The creation context supplies `10` for a bulk item when the attribute is absent; the base `Item` schema itself defaults to `0`. Do not assume direct schema/Repo inserts use the context default.

Warehouse stock queries aggregate `ItemsLocation` rows at warehouse locations. Low-stock queries compare that aggregate with `min_stock`; single items normalized to `0` do not trigger the threshold. Category values are the enums on [Item](../lib/licorice_lane/items/item.ex); the UI's `lighting` filter groups `:candle` and `:electric_light`.

`update_item/2` updates base item fields. Admin edits use `update_item_with_details/2` to update base fields and single-item condition/status in one transaction, including an image path change. Both APIs invalidate inventory data and broadcast after success. Neither provides a general operation for moving a single item or editing bulk quantity/location rows. New movement or rental write paths should handle all affected records in the context and invalidate any affected inventory/rental data.

## Customers, encryption, and search

[Customer](../lib/licorice_lane/customers/customer.ex) encrypts phone, email, contact person, billing address, and notes with `LicoriceLane.Encrypted.Binary`; the Vault uses AES-GCM. Name remains plaintext. Changesets populate email/phone hash fields using `Cloak.Ecto.SHA256`. Context queries support name substring search plus exact email/phone matches and deduplicate combined results.

The custom [HMAC type](../lib/licorice_lane/hashed/hmac.ex) is configured but unused by the current customer and message schemas. Production nevertheless requires `HMAC_SECRET` because runtime configuration explicitly reads it. See [encryption notes](../ENCRYPTION_IMPLEMENTATION_STATUS.md) before changing key management or lookup behavior.

Customer search pagination currently builds the combined search result list and slices it in memory. The unfiltered customer list uses database pagination. Avoid introducing partial matching over encrypted fields or logging loaded customer structs.

## Rentals and booking terminology

Bookings and rentals refer to the same `Rental` entity. `RentalSingleItem` connects a rental to a `SingleItem`; `RentalBulkItem` connects a rental to an `Item` with a quantity.

`Rentals` currently provides read queries, preloads, status filtering, and search. It has no create/update/delete context API. Seeds and rental fixtures insert records through Repo directly.

- Stored statuses: `:active`, `:returned`, `:late`, `:cancelled`.
- Upcoming queries use future `rented_at`, not `event_date`, and do not add a status restriction.
- Active queries check `status == :active` without excluding future dates.
- Overdue queries require past `return_by`, missing `returned_at`, and status in `[:active, :late]`.
- Event type is an enum of wedding, corporate, or birthday; dates use UTC datetimes.

These describe current query behavior. Revisit the business rules deliberately when implementing rental lifecycle operations.

## Admin shell and shared presentation code

[AdminLive](../lib/licorice_lane_web/live/admin/admin_live.ex) owns the active tab, editing item ID, and new-message count. It renders tab-specific LiveComponents from the same directory: dashboard, inventory, add item, edit item, bookings, clients, and messages. Component events target the component; navigation requests use `send(self(), ...)` messages handled by the parent LiveView.

Admin routes use both authentication/admin plugs and LiveView `on_mount` hooks. `Accounts.User.admin` defaults to false and is not cast by registration. [README](../README.md#local-admin-access) explains local account bootstrap.

[AdminHelpers](../lib/licorice_lane_web/helpers/admin_helpers.ex) holds labels, price/date formatting, truncation, pagination metadata, and the default page size of 25. [Pagination](../lib/licorice_lane_web/components/pagination.ex) renders pagination controls. Context pagination functions return `{records, total_count}` and use [Pagination](../lib/licorice_lane/pagination.ex) to clamp page bounds before fetching rows. Queries include a unique ID tie breaker so equal names/timestamps have stable page boundaries. Components use the same bounds for metadata, preserve filters/page on updates, and reset streams after changing filters or pages. Booking status/date controls are inside forms so LiveView can send change events; date filtering remains a placeholder. Public inventory has its own presentation helpers in [inventory_components.ex](../lib/licorice_lane_web/components/inventory_components.ex).

## Cache and realtime contracts

`Cache` exposes fetch/get/put/clear helpers and four invalidation functions. Current inventory, customer, and message writes call invalidation, but application query paths do not call `Cache.fetch/get/put`. Do not describe the current lists or dashboard as cached simply because Cachex is supervised.

| Invalidation function | Keys removed |
| --- | --- |
| `invalidate_inventory/0` | `:inventory_items`, `:low_stock_items`, `:dashboard_stats` |
| `invalidate_customers/0` | `:customers`, `:dashboard_stats` |
| `invalidate_rentals/0` | `:rentals`, `:dashboard_stats` |
| `invalidate_messages/0` | `:messages`, `:new_messages_count` |

`invalidate_rentals/0` exists for future rental write paths; the current read-only Rentals context does not call it. Direct Repo writes bypass context invalidation and broadcasts.

| Topic | Emitted messages | Producers / current consumers |
| --- | --- | --- |
| `"inventory:updates"` | `{:inventory_updated, item_id}` | Successful item creation/update/deletion; public InventoryLive subscribes and reloads its listing |
| `"messages"` | `{:message_created, message}`, `{:message_updated, message}` | Successful message creation/admin update; AdminLive refreshes its new-message count |

Message deletion invalidates cache entries but does not broadcast a deletion event. The dashboard/messages components also contain subscriptions and `handle_info` functions. LiveComponents share their parent's process: subscriptions deliver messages to the parent LiveView, not directly to component callbacks. AdminLive currently acknowledges inventory events without refreshing child components and handles message events by refreshing only its badge. Verify and implement explicit parent-to-component refresh when changing realtime UI behavior; see [status](STATUS.md#verification-gaps).

## Upload storage

Admin add/edit components keep their file inputs mounted during previews and initialize separate upload configurations once in `mount/1`. Routine component updates preserve form/upload state; changing the edited item cancels the previous selection. Add success cards display the saved image.

[InventoryImageUpload](../lib/licorice_lane_web/helpers/inventory_image_upload.ex) coordinates upload consumption with context persistence. It copies a completed image, runs the inventory save, and consumes only on success. Database or storage errors postpone consumption so correction/retry or cancellation can use the same temporary image. Failed-save copies are removed. Ecto transactions do not roll back filesystem writes.

[ImageStorage](../lib/licorice_lane/inventory/image_storage.ex) creates UUID filenames and uses the application's `priv/static/uploads` directory by default. `INVENTORY_UPLOAD_DIR` configures another local directory at runtime; a dedicated `/uploads` static plug resolves the same directory for serving. PostgreSQL stores only the `/uploads/...` path. Replaced images remain on disk because paths may be shared; automated old-image cleanup is not implemented. Storage remains local; see [status](STATUS.md#verification-gaps) for deployment concerns.

[Upload regressions](../test/licorice_lane_web/live/inventory_upload_test.exs) cover real admin component selection, saving/serving, retries, cancellation, parent/component refresh, storage errors, add/edit transitions, switching edited items, and rejected files. An optional [Playwright browser case](../test/browser/inventory_upload.cjs) exercises the actual JavaScript preview and upload flow; README documents its runtime settings.
